# 模型裁剪可行性分析：DSV4.1-Flash on M4 Pro 48 GB — 目标「编码正确率 ≥ 99.5%，TTFT/TPOT 提升 20×」

日期：2026-10-28 ｜ 基线：DeepInfer-Mac，专家缓存 9 GiB，解码 416 ms/token（2.4 tok/s），14 token 提示词 TTFT 7.8 s

## 结论
**在本机（M4 Pro，273 GB/s 统一内存带宽）上，20× 目标不可能通过模型裁剪在 99.5% 精度约束下达成**，有两条独立的硬上限：
1. **带宽下限**：即使全部权重驻留内存、SSD 等待为零、kernel 效率 100%，每 token 仅 dense 骨干（8.2 GB mxfp8）就要读 30 ms，加上 6 个专家约 10 ms，下限约 40 ms/token；20× 目标是 21 ms/token，低于物理下限。
2. **裁剪空间**：实测代码提示词上的专家路由分布显示，保留 99.5% 路由质量平均需要 220/384 个专家；裁到一半（192）会丢失 4.8% 的 held-out 路由质量，远超 0.5% 的精度预算。能「无损」剪掉的专家不到 20–40%，带来的加速 ≤ 1.3×。

可实现区间：组合「更大缓存 + 轻度专家裁剪 + `--moe-topk 4` + 引擎优化」约 2–3×（5–8 tok/s）；20× 只能换硬件（见第 5 节）。

## 1. 每 token 时间去哪了（实验：`scripts/profile_parts.py`，带同步）
| 组件 | ms/token | 说明 |
|---|---|---|
| MoE 专家（读取 + gather_qmm） | 292.7 | 其中 SSD 等待 234 ms（2.47 GB/token，命中率 0.45），GPU 专家计算约 60 ms |
| Attention 投影 | 68.9 | 40 层 ×（q/kv lora 投影），带宽+dispatch 开销 |
| Attention 核心 | 65.0 | 稀疏索引注意力 |
| 路由 + 共享专家 | 62.7 | 每层 gate + 共享专家 |
| 索引器/压缩器 | 6.5 | |
| **合计** | **521** | 不带同步实测 416 ms |

即使 SSD 等待归零，**计算侧仍有约 290 ms/token**（无同步时约 180 ms），只能得到约 1.7–2.3× 的 TPOT 改善。

## 2. Roofline（理论）
- 解码每 token 激活参数 ≈ 16B：dense 约 7B（FP8/mxfp8，8.2 GB）+ 6 × 40 × 35.4M = 8.5B 路由专家（2/3-bit，约 2.8 GB）+ Engram 查表（KB 级）。
- M4 Pro 统一内存带宽约 273 GB/s → 最少 (8.2 + 2.8) GB / 273 GB/s ≈ **40 ms/token**，对应 25 tok/s 的绝对上限（全驻留 + 理想 kernel）。
- 目标 20× = 21 ms/token（48 tok/s）< 40 ms 下限。**要达标必须把 dense 骨干也砍掉一半以上**（删层/删 attention 头），这与 99.5% 精度不相容。
- TTFT：14 token 提示词触达约 84 专家/层 × 40 层 × 15 MB ≈ 50 GB 专家读取，SSD 5–7 GB/s → 7–10 s，与实测 7.8 s 一致。20× = 0.4 s 要求这 50 GB 常驻内存，48 GB 机器不可能。

## 3. 专家路由覆盖实验（`routing_coverage.py`）
12 条多语言代码提示词（Python/C++/CUDA/Rust/Go/SQL/JS/Java/Bash/PyTorch）共 621 token，2 条 held-out 共 98 token，记录 40 层每个 token 的 top-6 路由权重。

| 覆盖路由质量 | 平均需保留专家数（/384） | 可裁剪比例 |
|---|---|---|
| 95% | 142 | 63% |
| 99% | 202 | 47% |
| **99.5%** | **220** | **43%** |
| 99.9% | 243 | 37% |

held-out 提示词在被裁剪后丢失的路由质量：裁到每层 48 个 → 29.0%；96 个 → 15.5%；192 个 → 4.8%。
两个关键观察：
- 仅 621 token 就已用到每层 200–317 个专家，使用集合随数据量持续增长，说明 DSV4.1-Flash 的专家没有「代码专用子集」，负载均衡训练使路由接近均匀。
- 路由质量损失不等于精度损失，但 0.5% 精度预算下经验上只允许 ≤1% 路由质量损失，对应保留约 240+/384 → 专家字节减少约 35%，缓存命中率从 0.45 升到约 0.55，**TPOT 改善约 1.2×**。

## 4. 各手段的可达加速（本机）
| 手段 | TPOT 预期 | 精度风险 | 依据 |
|---|---|---|---|
| 关大应用，缓存 9→24 GiB | 1.3–1.5× | 无 | 论文命中率模型：容量 1.5× → 命中 +0.09 |
| 轻度专家裁剪（保留 ~240/384，代码校准） | 1.1–1.2× | 低但非零，需基准验证 | 第 3 节 |
| `--moe-topk 4` | 1.38×（实测 3.35 tok/s） | 中，探针仍正确 | `logs/tune/results.tsv` |
| 引擎优化：减少同步、融合 attention 投影、DSpark 推测解码（专家命中高时） | 1.3–1.5× | 无 | profile：attention+路由 200 ms 中大半是 dispatch 开销 |
| **全部叠加** | **约 2.5–3.5×**（6–8 tok/s） | 需 ≥99.5% 基准验证 | |
| 全驻留理论极限（任何 48 GB 手段都达不到） | ≤ 10×（25 tok/s） | | roofline |

TTFT 可达 1.5–2×（更大缓存 + `--prefill-topk 4`）。

## 5. 达到 20× 的真实路径（换硬件，不裁模型）
| 平台 | 预期 TPOT | 说明 |
|---|---|---|
| Mac Studio 512 GB（M3/M5 Ultra，~800 GB/s） | 20–30 tok/s（8–12×） | 全部驻留，oMLX/mlx-lm 社区实测 20–29 tok/s |
| 单台 8× B200 / GB200 + 官方 DeepInfer | 50–150 tok/s/序列（20–60×） | 官方支持平台，FP8/FP4 张量核，DSpark 推测解码 |
| 本机 + 远端 GPU 后端 | 20×+ | 本机只做客户端/路由 |

## 6. 如何验证「99.5% 编码正确率」
本机 2–3 tok/s 下跑 HumanEval+（164 题 × ~300 token）每配置约 7 小时，LiveCodeBench 更长。可行替代：
1. teacher-forced top-1 一致性 + NLL（`scripts/score_api.py` 对 antirez/ds4 的 API 向量）：每配置数十分钟，对裁剪敏感。
2. 小规模代码子集（HumanEval 前 40 题）pass@1 对比基线，接受 ±1 题噪声。
3. 真正的 99.5% 判定需要在 GPU 服务器上用完整基准跑基线与裁剪版。

## 7. 建议
- 不在本机追求 20×；把本机定位为功能正确的低吞吐后端（已完成验证）。
- 若需要更快的本地体验，按第 4 节顺序做：先关应用放大缓存，再 `--moe-topk 4`，最后考虑代码校准的 35% 专家裁剪并用 score_api 验证。
- 若 20× 是硬指标，迁移到官方 DeepInfer 支持的 GPU 平台或 512 GB Mac Studio。
