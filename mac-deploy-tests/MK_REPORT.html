DSV4.1-Flash 单用户解码优化

在 48 GB 的 M4 Pro 上做 BS=1 解码：megakernel 把计算路径从 87 压到 68 ms/token，但端到端瓶颈是 SSD 读专家。TPS=10 只在有损的缓存感知路由（--fast）下达到。

TPS=10 只在有损的「缓存感知路由」下达到。 16 GiB 缓存时 LRU 命中率约 67%，每 token 约 78 次专家读盘 × 2.56 ms（15.5 MB / 6 GB/s）；即使未来全知的 Belady 缓存也要约 46 次读盘（~120 ms），所以无损 10 TPS 在这台机器上物理不可达。kernel 融合只能压缩计算（87→68 ms），压不掉 SSD。

做了什么

mHC megakernel：hc_post + mixes GEMV + Sinkhorn（20 轮）+ pre-mix + RMSNorm 一次 dispatch（最后一个 threadgroup 收尾）是计算路径 87→75 ms（原来每层 ~160 个微小 kernel）
稀疏注意力 megakernel：window ring + 索引器选中的压缩 KV gather、QK、sink softmax（PV 用 bf16 概率，同参考）、逆 RoPE、fp8 输出量化、ring 更新是注意力核心 ~100 µs/层 → 30 µs
mxfp8 GEMV：融合 act_quant / RMSNorm prologue、分组行（wo_a）、RoPE epilogue（wq_b）、split-K是与 MLX 持平或更快（190–240 GB/s）
router + shared expert 两次 dispatch：bf16 gate（省 157 MB 内存）、top-6 + 权重、下一/二层专家预测都在 kernel 内是280→194 µs/层
MoE megakernel：slab 槽位上的 6 个专家 up/down 两次 dispatch，宽读取 + 预缩放激活是2/3/4-bit 全部快于 MLX gather_qmm 链
索引器精确捷径：压缩 key ≤ 512 时 top-k 就是全部 key是（精确）短/中上下文省 ~300 kernel/token
GPU hot-wait：Apple GPU 空闲 ≥1–2 ms 后降频，下一个 kernel 慢 2–4×；等 SSD 时持续提交微小 kernel 保持时钟是无损解码 281→213 ms/token
原生 C 双优先级 IO（需求读独占 SSD，投机读低优先级、可提升、可取消）是与旧 IO 持平，去掉 GIL 争用
Engram 行在 token 开始时预取是−9.5 ms/token
top-p 采样只排序前 2048 候选（60 次随机校验结果一致）是采样 11→2 ms/token
缓存感知专家替换 --sub-rank N：第 N 名及以后的专家若不在缓存，用缓存里分数最高的未选专家替代，权重重新归一否见速度—质量前沿

所有 kernel 均对照 MLX 参考链验证（多数逐位一致，其余在 fp32 求和顺序误差内）；端到端偏差与「只改 fp32 求和分组」的偏差同量级（模型对数值扰动本身是混沌的）。pytest tests/ 33/33 通过；部署期的 API 端到端套件 test_api_e2e.py 在新引擎（无损默认）上 28/28 通过（流式、贪心确定性 + logprobs、seed、多轮前缀复用、工具调用、JSON schema + thinking、6K/12K 长上下文 needle、视觉、/v1/messages、/v1/responses）。

速度—质量前沿（cache 16 GiB）

质量：官方 API 采样续写（antirez/ds4 V4.1-Flash 向量）的 teacher-forced NLL 与 top-1 一致率，与无损配置逐例配对，95% bootstrap 区间。速度：200 token 贪心稳态（第 20 个 token 之后）。

规律：速度与质量代价都随「被替换的专家数」近似线性变化；替换优于丢弃；分数差（gap）限制每次替换的质量代价最低，但换来的速度也少。

--fast 功能回归：API 端到端套件 26/28 通过：精确答案、生成代码可执行、JSON schema、工具调用、6K/12K 长上下文检索、视觉全部通过；失败的 2 项是「同一贪心请求两次输出一致」与「同 seed 可复现」。这是缓存感知路由的固有性质：替换哪个专家取决于当时缓存里有什么（受之前的请求和 SSD 时序影响），所以 --fast 的输出不可复现；需要确定性输出时请用默认无损模式。

为什么无损做不到 10 TPS

  • 计算侧：每 token 读 ~11 GB 常驻权重（dense mxfp8 5.2 GB + 共享专家/路由 1.8 GB + 6 个路由专家 3.5 GB + head 0.7 GB）；现在 GPU 内核 54 ms，带宽下限 ~48 ms。
  • SSD 侧：logs/mk/traces/trace_c16.npz（960 个解码 token 的完整路由分数）离线回放：LRU 0.674 命中 → 78 读/token；Belady 0.811 → 46 读/token；LFU / 2Q / 衰减 LFU / 按名次刷新都不优于 LRU；缓存 24 GiB → 61 读/token。
  • 时序模型 sim_pipeline.py：计算压到 48 ms、--sub-rank 3、16 GiB 时约 110 ms/token；要到 100 ms 需要再大缓存或更激进的替换。
  • 自投机（DSpark MTP）：每轮只接受 ~1.9 token，验证要读所有草稿 token 的专家并集，SSD 受限下反而更慢（2.5–2.8 tok/s），已放弃。

还能做什么

  1. 更大的专家缓存最有效（需要关掉其他应用、放宽 CLAUDE.md 的 16 GiB 上限）：24 GiB 时读盘 −22%，--sub-rank 3 有望接近 10 TPS。
  2. 外置 Thunderbolt 5 SSD 与内置盘条带化（专家文件分两半）：SSD 带宽翻倍是唯一能直接解决无损瓶颈的硬件手段。
  3. GPU 侧专家调度（命中专家不等 CPU 同步）：逐层同步的总开销约 6 ms/token（计算路径实测：无逐层同步 61.6 ms 对比有同步 67.8 ms），这是上限；其中路由同步到首个 MoE kernel 的 CPU 侧延迟实测 ~67 µs/层（≈ 2.7 ms/token）。
