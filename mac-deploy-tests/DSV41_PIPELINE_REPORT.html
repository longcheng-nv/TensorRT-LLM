DSV4.1-Flash 在 agent 里的推理流水线：气泡在哪

在服务端录下一段真实的 DeepSeek Harness 会话（三轮，6 个请求），再在同一个引擎上按服务端的方式回放：逐层记录 CPU 主线程的各阶段、由主机同步推断的 GPU 区间，以及原生 IO 每个 2 MB 读块。配置与平时用 dsv41 时一致：默认 --fast，专家缓存 8 GiB。dsv41 启动时按当时的空闲内存选缓存（6–16 GiB）：11-24 是 8 GiB，今天先后是 6 和 14 GiB，所以 agent 里的解码速度会跟着变。

结论

  • prefill 是读盘受限，而且读得很多。新 token 只有 14–15 个的请求也要读约 22 GB、首字前 4 s 多：prefill 必须精确路由，每层要把这些 token 用到的专家都读进来，8 GiB 缓存几乎留不住上一层的专家。
  • 最明显的气泡在层与层之间。每层最后一批专家读完后，SSD 要等下一层算完注意力和路由才知道读什么，这段时间完全空闲：全会话 10.5 s，冷 prefill 每层 200–300 ms。
  • 已实现跨层预读，默认打开（DEEPINFER_PREFILL_LOOKAHEAD=16，设 0 关闭）。在本层最后一批时，用下一层的路由器对本层输入预测、按行数读入最可能的专家。首字前合计 -12%，冷 prefill -14%，带图 prefill 约 −17%；只改读盘时机，不改计算。
  • 顺带查清：prefill 本身不能逐位复现。专家结果用 MLX 的 scatter-add 加回各行，GPU 上是原子加；一行在同一批里命中两个专家时，累加顺序不固定。带图 prompt 上同一设置的两次运行 logits 最多差 1.125（top-1 不变）。与预读无关，修法见「下一步」。
  • 解码没有明显空泡。两者都空闲每 token 只有 1–2 ms；慢在 8 GiB 缓存下每 token 要等盘 42–77 ms（16 GiB 时 15.6 ms），这是缓存容量问题。
  • 更大的一块是重复工作，不是气泡。每个新会话都要重算同一段约 1,489 token 的 system 提示和工具定义（这部分不含当前目录、时间等动态内容），冷 prefill 31 s。给这段共享前缀留一个快照，新会话就能直接复用。

方法：录一段真实会话，在引擎上逐层回放

  • 录制。mk/agent_capture.py 在 8000 端口起与 dsv41 相同的服务（默认 --fast，缓存 8 GiB），记录每个请求的提示 token、生成 token 和服务端统计；然后用真实的 dsv41 -p … -p … -p … 跑三轮任务：列文件并总结 README、追问依赖、把总结写进文件。
  • 回放。mk/trace_agent.py 在一个新进程里按服务端的方式逐个请求做 prefill（前缀复用、分块、Bounded Replay 都与服务端相同），再把当时生成的 token 逐个喂回（teacher forcing）。这样每个请求的 prefill 量、解码工作量和下一请求能复用的前缀都和实际运行一致。
  • 记录。CPU 主线程逐层的阶段（prefill 时每层按 16 个专家一批：预读下一批 → 等这一批读完 → 构建 → 等 GPU 算完），原生 IO 每个 2 MB 读块所在的线程与起止时刻。GPU 区间是推断的：这台 Mac 拿不到 GPU 时间戳，块的结束取主机同步返回的时刻。

回放与实际运行吻合：复用的前缀长度完全一致，读盘量相差不到 1%；首字时间差 −10% 到 +5%（实际运行多了 HTTP、分词，以及服务刚启动时的冷页缓存）。

时间去向：首字前与解码

prefill：读盘受限，空泡在层交界

层内几乎没有空泡：「等这一批专家读完」的 61 s 里 SSD 只空了 0.17 s。不过单个 IO 线程在两个读块之间平均空约 0.7 ms（一个 2 MB 读块约 1.9 ms），8 个线程平均只有 5–6 个在读，SSD 忙时带宽 5.4–6.1 GB/s。更深的队列能不能把带宽再推高，要单独做 IO 微基准。

跨层预读：把层交界的 SSD 空泡填上

做法：每层算路由时，顺带用下一层的路由器对本层的输入打分，在同一次主机同步里拿回每行的 top-6，按被预测的次数排序。本层进入最后一批专家时（本层已经没有要读的了），按低优先级读入下一层最可能的 max(16, 行数 ÷ 12) 个专家。下一层路由出来以后，还没开始读的猜错项会被取消。专家批的顺序和计算都不变。只在 prefill 里生效（LLM._prefill / _prefill_vl 打开 Transformer.prefilling），解码与 DSpark 的多 token 前向不受影响。代码在 deepinfer_mac/model/model.py（MoE.PREFILL_LOOKAHEAD），默认打开，DEEPINFER_PREFILL_LOOKAHEAD=0 关闭。

  • 文本 prefill：mk/test_prefill_lookahead.py 用真实模型做「非末块 + 末块（Bounded Replay）」两块 prefill，开 / 关交替各两次：18,099,200 个 logits 四次逐位相同；耗时 32.4 / 34.1 s → 28.0 / 28.5 s，读盘 165.3 → 166.1 GB。
  • 带图 prefill：mk/bench_prefill_vl.py（dsh 的 system 文本 + 测试图片，1,500 token）：28.3 / 27.1 / 30.5 / 27.6 s → 23.6 / 22.7 / 23.5 / 23.4 s（约 −17%）。这条路径上 prefill 本身就不能逐位复现（见下一条），按结果分组时，组别与开关无关。
  • prefill 的运行间差异（原有）：连续 7 次带图 prefill 分成两组逐位相同的结果，组别与开关、是否清空缓存都无关；逐层校验和显示前 21 层完全相同，第一处差异在第 21 层 MoE 的输出，而它的输入、路由、共享专家都相同，槽里的专家字节也与模型文件一致。原因是 MLX 的 scatter-add（y.at[r].add(o)）在 GPU 上用原子加：同样的输入重复 30 次，结果就不逐位相同。记录在 logs/mk/agent/prefill_nondeterminism.md。
  • 单测：pytest tests/ 40/40 通过（tiny checkpoint 上的引擎、与参考实现的一致性、视觉、存储、服务端）。
  • 端到端：dsv41 test --quick 走真实启动器（这次按空闲内存选了 14 GB 缓存）7/7 通过：问答、文件创建与修改、前缀复用、带图、终端 -p、@ 引用；新会话第二个冷请求首字 26.1 s（11-24 为 30.3 s）。
  • 解码：预读只在 prefill 里；两次回放的解码均值 139.9 → 145.2 ms/token，差 +3.8%，在运行间 ±3–5% 的波动范围内（稳态 token 也差这么多，与 prefill 后的缓存内容无关）。

解码：没有明显空泡，慢在缓存容量
