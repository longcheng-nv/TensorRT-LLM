Verdict: FALSIFIED — NO-SHIP in the DSv4 decode regime (flag stays OFF, default = unchanged baseline).

The optimization targets HBM input-read passes, but on B200 the baseline already does ~1 HBM pass: the decode-regime input (≤1.05 MB at N=262144) is ~126× smaller than L2 (132.6 MB), so the baseline's 2nd/3rd logical passes are served from cache, not HBM. The kernel is in fact L1/TEX-throughput-bound on a single CTA (DRAM utilization 0.25%). Candidate compaction therefore saves zero memory traffic and only adds per-element work + a scatter → it loses +68% / +93% / +106% at N=65536 / 131072 / 262144. The implementation is numerically exact; it is simply the wrong lever for this regime. The 40% target is physically unreachable here via this algorithm.

1. The algorithm under test

Inspired by SGLang's radix-histogram search narrowing. For a guessed threshold t, maintain a candidate buffer of size C·K:

  • Undershoot (count(≥t) < K): the ≥t elements are confirmed top-K winners; lower the threshold by secant interpolation between (t, count) and (min preIdx value, ·), and search only the residual region for the remaining K−count.
  • Overshoot (N_cand = count(≥t) ≥ K): if N_cand > C·K run a full-N secant count_ge for a higher threshold; converge when K ≤ N_cand ≤ C·K → copy the candidate buffer to shared memory and do an exact size-N_cand top-K refine.

Goal: drive total HBM element scans toward ≈ 1.

Genuinely new vs current GVR: (N1) cross-iteration candidate buffering — compact survivors to a global scratch on pass 1 so later evals + P3 read the shrunken set; (N2) the undershoot fast-exit. The "refine in smem" and the secant are already GVR.

2. Hypothesis & pre-registered ceiling

Host-replay on the report data showed the baseline does 3 logical full-N reads at large N (2 P2 secant evals + 1 P3 collect), with a final candidate count of only ≈4.3–4.6×K. Using op13's phase fractions (P2+P3 ≈ 80% of time at N=262144), reducing 3 passes → ~1 appeared to offer ~40–50%. This estimate was wrong — it assumed pass-count equals HBM traffic. It does not (see §4).

4. Root cause — independently confirmed with ncu

The premise "baseline = 3 HBM passes" is false on B200. Measured on the baseline GVR kernel at N=262144 fp32 (ncu, single gated launch):

Physical picture for the DSv4 decode regime (N ≤ 262144 ⇒ input ≤ 1.05 MB ≪ L2 = 132.6 MB):

  • After pass 1 loads the tiny input, it is fully cache-resident. The baseline's later P2/P3 passes are L1/L2 hits, costing ~0 HBM traffic. The baseline already exceeds the "≈1 HBM pass" goal.
  • The kernel is L1/TEX-throughput-bound on one SM (BS=1 → 1/148 SMs). Cost is the serial per-element work over N on a single CTA.
  • Compaction replaces cheap count-passes with a pass-1 that does more L1 work per element (warp ballot/popc/shuffle) plus a global scatter write and scratch re-reads → strictly more L1/TEX traffic → net loss that grows with N.
Lesson (recorded as a learning): before optimizing input-pass count, verify it is actually HBM traffic with ncu dram__bytes_read.sum. When the working set fits L2, "fewer passes" is a no-op (or worse) — the baseline already gets cache reuse. op13/op12 had flagged "reduce P2 passes" as the big unexploited lever; this measurement shows that lever is only real when the input exceeds L2.

5. Exactness (the implementation is correct)

  • fp32: 72/72 cells value-equivalent to torch.topk (K∈{512,1024} × N∈{131072,262144} × 3 cfgs × 3 seeds) — independently re-run here.
  • Agent's wider grid: 214/216 strict pass. The 2 fails (K1024 bf16, N262144, beta_shallow) are a pre-existing bf16 boundary-tie defect that hits the baseline identically (27 elements tie at the K-th bf16 value) — not a 1pass regression; 1pass is value-equivalent to base on every cell.
  • Fast-path exactness gate K ≤ c0 ≤ cap with fallback to the baseline path on undershoot/overflow — correct for any distribution.
  • Default flag is OFF ⇒ the production/baseline path is byte-identical and cannot regress.

6. When this algorithm would win

Only when the input exceeds L2 so that multiple passes each hit DRAM: N > ~33M fp32 elements (>126 MB), far outside the DSv4 sparse-attention decode regime (N ≤ 262144). The exact fp32 fast path + fallback are retained in the code for any such future >L2 regime, behind the OFF-by-default flag.
