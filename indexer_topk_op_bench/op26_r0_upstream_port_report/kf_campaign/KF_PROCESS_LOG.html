1 · What KernelFactory is, and how its harness works

KernelFactory (kf CLI, kernelfactory.nvidia.com) is NVIDIA's multi-agent GPU-kernel optimization platform. You define a problem in the CudaGym/SOLBench schema; the platform then runs a campaign: sequential rounds, each spawning a pool of LLM coding agents in parallel (here: 2× Claude Fable-5 @max + 2× Codex GPT-5.6-sol @xhigh + 2× N3 Claude-Opus-4.8) that write CUDA kernels, evaluate them on real GPUs, see each other's results and insights from earlier rounds, and evolve solutions via mutation / crossover / random strategies until the round budget, a convergence target, or a stagnation limit ends the campaign.

1.1 The evaluation harness (CudaGym / SOLBench)

ComponentRole in the harness
definition.jsonThe problem contract: named axes (const / var / derived-expr), inputs/outputs as ordered tensor specs (shape strings refer to axes; scalars use shape:null), a pure-PyTorch reference implementation (def run(...)) used as ground truth, and an optional custom_correctness_entrypoint replacing the default elementwise-tolerance check.
workload.jsonlOne test case per line: concrete axis values + input sources (random / scalar / safetensors blob / custom generator). Per-workload custom_correctness_kwargs are passed as kwargs into the custom checker.
baselines.jsonlPer-workload target timings ({"uuid", "execution_time_ms"}). Candidate speedup = baseline_time / candidate_time per workload; the campaign's fitness aggregates speedup + correctness (+ efficiency, novelty) with 40/30/20/10 default weights.
SolutionAn agent submission: source files + build spec. CUDA C++ solutions are built with tvm_ffi.cpp.build into benchmark_kernel.so (TVM-FFI TensorView ABI, inputs first then outputs, no torch/extension.h). The eval driver loads it, generates/loads inputs, runs correctness then a warm-up + timed benchmark loop (CUDA-event based) per workload, and records a Trace (status, latency, speedup, logs).
Compliance judgeAn LLM judge inspects every submission: CUDA-graph capture/replay banned (would measure launch amortization, not kernel work) and framework-kernel imports banned (flashinfer / trtllm / tensorrt_llm at any level) — kernels must be original computation.
Agent-side toolsInside the agent pod: compile server, GPU eval server, ncu/nsys/compute-sanitizer profiling, a shared DB of all candidates + inter-agent insights messaging.

2 · Problem encoding (what the agents optimize)

Op: top-K index selection over one real captured indexer-logits row (BS=1, fp32): inputs logits[1, npad] (npad = ceil(n/64)·64, tail padded with fp32-min), pre_idx[1, k] (previous decode step's top-K = temporal warm hint), scalar n_valid; output indices[1, k] int32, any order.

Correctness: tie-robust set semantics via custom_correctness_entrypoint=check_topk: per workload we precomputed mandatory (values > k-th value — must all be present) and tie (values == k-th value — any subset may fill the rest); checker also enforces uniqueness and range. This mirrors the PR#16457 equivalence-test semantics (index-set, tie-either-way).

Workloads: 28 stratified real cells from the 865-cell §4 grid — 3 models (Flash K=512 / Pro K=1024 / V3.2 K=2048) × ISL rungs (4k→1M) × {min-hit, max-hit} layer per rung. Hit range 0.023–1.0; N range 1027–262127; assets 9.8 MB safetensors.

Baseline: per-cell PR#16457 GVR timings from real_3arm_layers_full.csv (pr column; nsys pure-kernel cold-L2 on umbriel-b200-027), 5–29 µs, geomean 14.40 µs. Methodology caveat: campaign eval times warm-loop CUDA events on the managed pool, so campaign-reported speedups are steering signals, not the verdict — the acceptance gate is a local 865-cell nsys cold-L2 paired A/B on our own B200s.

Prompt steering: prompt.md distills the GVR falsification history (12+ dead ends: fused count+collect, smem staging, secant multi-round, CUB sort, single-CTA occupancy wall) and points at the two live structural levers: multi-CTA-per-row cooperation (sglang-style ≈1.4× existence proof) and histogram/radix select over fp32-ordered-uint keys; requires geomean ≥1.30× with no cell below ~1.05× (margin over the +20% final bar).

1 · KernelFactory 是什么,harness 原理

KernelFactory(kf CLI)是 NVIDIA 的多 agent GPU kernel 优化平台。 用 CudaGym/SOLBench 格式定义问题,平台跑战役(campaign):顺序执行多个 轮次,每轮并行拉起一池 LLM 编码 agent(本战役:2× Claude Fable-5 @max + 2× Codex GPT-5.6-sol @xhigh + 2× N3 Claude-Opus-4.8),它们编写 CUDA kernel、在真 GPU 上评测、 共享历史轮次的候选与洞察,以变异/杂交/随机策略演化解,直到轮次预算、收敛目标或 停滞上限终止。

1.1 评测 harness(CudaGym / SOLBench)

组件在 harness 中的角色
definition.json问题契约:axes(常量/变量/表达式派生)、 按序的 inputs/outputs 张量规格(shape 引用 axis 名;标量用 shape:null)、 作为真值的纯 PyTorch reference 实现,以及可选的 custom_correctness_entrypoint(替换默认的逐元素容差检查)。
workload.jsonl每行一个测试用例:具体 axis 取值 + 输入来源 (random/scalar/safetensors blob/custom 生成器)。 每 workload 的 custom_correctness_kwargs 以 kwargs 传入自定义检查器。
baselines.jsonl逐 workload 目标时延。候选 加速比 = 基线时间 / 候选时间;fitness 按 40/30/20/10 聚合(性能/正确性/效率/新颖性)。
Solutionagent 提交:源码 + 构建规格。CUDA C++ 用 tvm_ffi.cpp.build 编译为 benchmark_kernel.so(TVM-FFI TensorView ABI)。 评测驱动加载后:先正确性、再 warm-up + CUDA-event 计时循环,逐 workload 记录 Trace。
合规裁判LLM 裁判审查每个提交:默认禁 CUDA graph(那是测发射摊销, 不是 kernel 本身)且禁框架 kernel 导入(flashinfer/trtllm 等任何层级)——必须原创计算。
agent 侧工具agent pod 内:编译服务、GPU 评测服务、 ncu/nsys/compute-sanitizer、全候选共享 DB + agent 间 insight 消息。

2 · 问题编码(agent 优化的目标)

算子:单行真实 indexer logits 的 top-K 索引选择(BS=1 fp32): logits[1,npad](尾部 fp32-min 填充)、pre_idx[1,k](上一 decode 步 top-K = 时间warm提示)、标量 n_valid;输出 indices[1,k] int32 任意序。

正确性:tie-鲁棒集合语义:每 workload 预计算 mandatory(严格大于第 K 值, 必须全含)与 tie(等于第 K 值,任意子集补足),另查唯一性与范围 —— 与 PR#16457 等价性测试同语义。

Workload:865-cell §4 网格的 28 个分层抽样 cell(3 模型 × ISL 梯 × 最低/最高命中层), hit 0.023–1.0,N 1027–262127,资产 9.8 MB。

基线:real_3arm_layers_full.csv 的 pr 列(nsys 纯 kernel 冷 L2,本机实测),5–29µs。口径注意:campaign 评测是 warm 循环 CUDA-event,其加速比 只是导向信号;判决门 = 本地 865-cell nsys 冷-L2 配对 A/B。

Prompt 导向:注入 GVR 证伪史(12+ 死路)与两条活杠杆(多 CTA 协作 = sglang ~1.4× 存在性证明;fp32-ordered-uint 直方图/radix 选择),要求几何均值 ≥1.30× 且无 cell 低于 ~1.05×。
